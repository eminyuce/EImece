# 7. Load Test Strategy

Use a progressive load test.

Do NOT immediately start with extreme traffic.

Run approximately:

### Level 1 — Smoke

5 concurrent users

Duration: 1 minute

### Level 2 — Light

10 concurrent users

Duration: 2 minutes

### Level 3 — Normal

25 concurrent users

Duration: 5 minutes

### Level 4 — Heavy

50 concurrent users

Duration: 5 minutes

### Level 5 — High

100 concurrent users

Duration: 5 minutes

### Level 6 — Extreme

250 concurrent users

Duration: only if the application remains stable.

Stop increasing load if:

* IIS becomes unhealthy
* error rate exceeds 5%
* database becomes saturated
* request queue grows continuously
* worker process memory grows uncontrollably
* response times become catastrophic
* SQL Server becomes unstable
* the application stops responding

The purpose is to find the application's limits, not to crash the machine unnecessarily.

# 20. Performance Thresholds

Use these as initial engineering targets, not absolute guarantees.

### Healthy

* HTTP error rate: < 1%
* p95: < 500 ms for normal read-heavy pages
* p99: < 1 second for normal read-heavy pages
* no sustained request queue growth
* no sustained memory growth
* no database blocking/deadlocks

### Warning

* HTTP error rate: 1–5%
* p95: 500 ms–2 seconds
* increasing IIS queue
* high SQL CPU
* increasing memory trend

### Critical

* HTTP error rate: > 5%
* p95: > 2 seconds
* continuous request queue growth
* worker process memory continuously increasing
* connection pool exhaustion
* deadlocks
* repeated HTTP 500
* IIS application pool recycling under normal load

Adjust these thresholds if the application architecture makes a different threshold technically justified.
