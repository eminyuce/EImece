# Security Code Review — EImece (ASP.NET MVC 5 / .NET Framework 4.7.2)

I reviewed configuration, authentication/authorization, the payment flow, cryptography helpers, file handling, and view rendering. Below are the concrete, exploitable findings ordered by severity, followed by lower-risk hardening items.

---

## CRITICAL

### C1 — Hard-coded database credentials in source-controlled config
**CWE-798 / CWE-259** · `EImece/EImece/Web.config` (line 15), `EImece/EImece.Tests/App.config` (line 15)

```15:15:EImece/EImece/Web.config
<add name="EImeceDbConnection" connectionString="Data Source=YUCE\SQLEXPRESS;Initial Catalog=yuva8905_yuvadan;User ID=sqluser;Password=sqluser;Encrypt=True;TrustServerCertificate=True;" providerName="System.Data.SqlClient"/>
```

SQL credentials are committed in plaintext. `TrustServerCertificate=True` also disables TLS certificate validation for the DB channel (MITM of the DB connection). Anyone with repo access gets DB credentials.

**Remediation:** Move the connection string to a machine-level secret store / `configBuilders` / environment variable, rotate the `sqluser` password immediately, and set `TrustServerCertificate=False` with a valid server certificate. Add `Web.config` secrets to `.gitignore` and use a `Web.config` transform / `configSource`.

---

### C2 — Hard-coded cryptographic key + static salt/IV protecting the payment flow
**CWE-321 / CWE-329 / CWE-798** · `EImece.Domain/Helpers/EncryptDecryptQueryString.cs`, `EImece.Domain/Helpers/StringCipher.cs`

```9:16:EImece/EImece.Domain/Helpers/EncryptDecryptQueryString.cs
private static string sEncryptionKey
{
    get
    {
        return AppConfig.GetConfigString("encrypt-password", "SAUW193BX628TD57"); ;
    }
}
```

```22:26:EImece/EImece.Domain/Helpers/EncryptDecryptQueryString.cs
using (Aes encryptor = Aes.Create())
{
    Rfc2898DeriveBytes pdb = new Rfc2898DeriveBytes(EncryptionKey, new byte[] { 0x49, 0x76, 0x61, 0x6e, ... });
    encryptor.Key = pdb.GetBytes(32);
    encryptor.IV = pdb.GetBytes(16);
```

`encrypt-password` is **not** present in `Web.config`, so the hard-coded fallback `"SAUW193BX628TD57"` is what runs in production. The same class derives a **fixed Key and fixed IV** from a **constant salt**, making the cipher deterministic (identical plaintext → identical ciphertext, no integrity/authentication).

This is used in the payment callbacks to protect the `userId` and `orderGuid`:

```574:579:EImece/EImece/Controllers/PaymentController.cs
var orderGuid = EncryptDecryptQueryString.Decrypt(HttpUtility.UrlDecode(o));
...
var userId = EncryptDecryptQueryString.Decrypt(HttpUtility.UrlDecode(u));
var order = ShoppingCartService.SaveShoppingCart(orderNumber, shoppingCart, checkoutForm, userId);
```

Because the key is public in the repo, an attacker can forge/repurpose `o` and `u` values (order/user reference tampering, IDOR-style order association). `StringCipher` shares the same default password constant, so any query-string values protected by it are equally forgeable.

**Remediation:** Remove the hard-coded fallbacks (fail closed if the secret is missing). Store the key in a secret store, use an authenticated cipher (AES-GCM) or the ASP.NET Data Protection API, and never derive a static IV — generate a random IV per message (as `StringCipher.Encrypt` already does). Rotate the key.

## HIGH

### H1 — Reflected XSS via `Html.Raw` of the search term
**CWE-79** · `EImece/EImece/Views/Products/SearchProducts.cshtml` (line 56)

```56:56:EImece/EImece/Views/Products/SearchProducts.cshtml
<span class="d-block mt-2">@Html.Raw(String.Format(Resource.SearchResultTotalCountText, Model.Search, productsAll.TotalCount))</span>
```

`Model.Search` is the attacker-controlled search query (bound directly from the request in the public `Products.searchproducts` action) and is emitted **unencoded**. This is a reflected XSS sink on a public, unauthenticated page.

**Exploitation note:** ASP.NET request validation (the app runs `httpRuntime targetFramework="4.5.2"`, so legacy validation is on) blocks the most naive `<script>` payloads, which reduces but does not eliminate exploitability (encoding tricks, non-`<` breakouts, or any code path that decodes/relaxes validation). The fix is cheap and should be applied regardless.

**Remediation:** Use encoded output — `@String.Format(Resource.SearchResultTotalCountText, Model.Search, productsAll.TotalCount)` (Razor auto-encodes), or `@Html.Encode`. Audit the other `Html.Raw` usages that render entity content (`Detail.cshtml` product `Description`/`ShortDescription`/comment `Review`) — see M4.

### H2 — Sensitive data written to application logs
**CWE-532 / CWE-201** · `AccountController.cs`, `PaymentController.cs`

Password-reset and email-confirmation flows log the callback URLs, which contain the single-use reset/confirmation **token**:

```500:502:EImece/EImece/Controllers/AccountController.cs
string code = await UserManager.GeneratePasswordResetTokenAsync(user.Id);
var callbackUrl = Url.Action("ResetPassword", "Account", new { userId = user.Id, code = code }, ...);
Logger.Info($"Generated password reset token. Callback URL: {callbackUrl}");
```

`ResetPassword`/`ConfirmEmail` also log `code` directly (`Logger.Info($"...code: {code}")`). Anyone with log access (or via the admin `AppLogs` viewer / log aggregation) can take over accounts by replaying the reset link. The payment controller additionally logs full serialized checkout forms and customer PII (`JsonConvert.SerializeObject(checkoutForm)`, emails, decrypted `userId`/`orderGuid`).

**Remediation:** Never log password-reset/confirmation tokens, callback URLs, decrypted identifiers, or serialized payment/PII payloads. Reduce these to `Logger.Debug` without secrets, and scrub PII. Treat reset tokens as credentials.

### H3 — Production `debug="true"`, `trust level="Full"`, downlevel `httpRuntime`
**CWE-11 / CWE-16** · `EImece/EImece/Web.config` (lines 80, 83, 84)

```80:84:EImece/EImece/Web.config
<trust level="Full"/>
<globalization culture="tr-TR" uiCulture="tr-TR"/>
<customErrors mode="RemoteOnly"/>
<compilation targetFramework="4.7.2" debug="true"/>
<httpRuntime targetFramework="4.5.2" maxUrlLength="2024" maxRequestLength="512000" enableVersionHeader="false" executionTimeout="36000"/>
```

- `debug="true"` in production leaks detailed errors, disables optimizations, and can expose source in stack traces.
- `httpRuntime targetFramework="4.5.2"` forces the framework into **4.5.2 quirks mode**, opting out of newer security defaults (cookie SameSite handling, header behaviors) even though compilation targets 4.7.2.
- `customErrors mode="RemoteOnly"` combined with `debug="true"` means detailed errors surface on the server and via any local/tunnel access.

**Remediation:** Set `debug="false"`, `customErrors mode="On"` with a `defaultRedirect`, align `httpRuntime targetFramework="4.7.2"`, and reduce `trust level` to `Medium`/`Full` only if a component truly requires it. Also lower `maxRequestLength` (currently ~500 MB) to a sane upload cap (see L2).

## MEDIUM

### M1 — Username/account enumeration on login and password reset
**CWE-203 / CWE-204** · `AccountController.Login`, `AdminLogin`, `ForgotPassword`

The failure branch distinguishes "no user" from "wrong password":

```246:264:EImece/EImece/Controllers/AccountController.cs
case SignInStatus.Failure:
    var user = ApplicationDbContext.Users.FirstOrDefault(u => u.UserName.Equals(model.Email));
    if (user != null) { ... InvalidLoginAttemptPasswordNotCorrect ... }
    else { ... Resource.NoUserFound ... }
```

`ForgotPassword` similarly returns `NoUserFound` for unknown emails. An attacker can enumerate valid accounts.

**Remediation:** Return a single generic message ("Invalid email or password") for all login failures, and a generic "If the account exists, an email was sent" for forgot-password.

### M2 — Account lockout disabled → password brute force
**CWE-307** · `AccountController.Login` / `AdminLogin`

```111:111:EImece/EImece/Controllers/AccountController.cs
var result = await SignInManager.PasswordSignInAsync(model.Email, model.Password, model.RememberMe, shouldLockout: false);
```

`shouldLockout: false` means failed attempts never lock the account. The only throttle is a trivially-solvable arithmetic captcha (see M6), so online brute force is feasible.

**Remediation:** Set `shouldLockout: true` and configure `MaxFailedAccessAttemptsBeforeLockout` / `DefaultAccountLockoutTimeSpan` in the user manager.

### M3 — Insecure authentication cookie / transport configuration
**CWE-614 / CWE-1275 / CWE-319** · `App_Start/Startup.Auth.cs`, `Web.config`

```25:37:EImece/EImece/App_Start/Startup.Auth.cs
app.UseCookieAuthentication(new CookieAuthenticationOptions
{
    AuthenticationType = DefaultAuthenticationTypes.ApplicationCookie,
    LoginPath = new PathString("/Account/Login"),
    Provider = new CookieAuthenticationProvider { ... }
});
```

`CookieSecureOption` and SameSite are not set; `UseSSL=false` in appSettings; there is no `<httpCookies requireSSL="true" ...>` and no HSTS. The auth cookie can be transmitted/accepted over HTTP and is not SameSite-scoped.

**Remediation:** Set `CookieSecure = CookieSecureOption.Always`, add `CookieSameSite = SameSiteMode.Lax`, add `<httpCookies httpOnlyCookies="true" requireSSL="true"/>`, enforce HTTPS (`RequireHttpsAttribute` / URL rewrite) and emit `Strict-Transport-Security`.

### M4 — Stored XSS in product reviews (moderation-gated) + no CSRF/anti-automation
**CWE-79 / CWE-352** · `EImece/EImece/Controllers/ProductsController.cs` (Review), `Views/Products/Detail.cshtml` (line 878)

Anonymous users can post reviews; the field is later rendered raw:

```878:878:EImece/EImece/Views/Products/Detail.cshtml
<p class="mb-0">@Html.Raw(productComment.Review)</p>
```

The action correctly sets `IsActive = false` (approval required), which limits impact, but there is **no output encoding/sanitization**, **no `[ValidateAntiForgeryToken]`, and no captcha**. An approved malicious review executes script in every visitor's browser (and admins during moderation).

**Remediation:** Encode on output or sanitize on input (e.g., HtmlSanitizer allow-list) for `Review`. Add `[ValidateAntiForgeryToken]` and captcha to the `Review` POST.

### M5 — CSRF on state-changing GET actions
**CWE-352** · `Areas/Admin/Controllers/FileUploadController.cs`, `PaymentController.cs`, `ProductsController.MoveProducts`

`FileUploadController` performs file deletion over **GET** with no anti-forgery token, and `Upload` (POST) has no token either:

```70:76:EImece/EImece/Areas/Admin/Controllers/FileUploadController.cs
[HttpGet]
public JsonResult DeleteFile(string file)
{
    var CurrentContext = HttpContext;
    filesHelper.DeleteFile(file, CurrentContext);
    return Json("OK", JsonRequestBehavior.AllowGet);
}
```

Public cart mutations (`AddToCart`, `UpdateQuantity`, `RemoveCart`, `sendOrderComments`) and admin `MoveProducts` are also GET/no-token. The admin ones are exploitable against a logged-in admin via a forged link/image.

**Remediation:** Make all state-changing actions `[HttpPost]` + `[ValidateAntiForgeryToken]` and submit the token from views. Never mutate state on GET.

### M6 — Weak/guessable CAPTCHA using `System.Random`
**CWE-330 / CWE-338** · `EImece/EImece/Controllers/ImagesController.cs` (GetCaptcha), `FilesHelper.GenerateCaptchaImg`

```216:225:EImece/EImece/Controllers/ImagesController.cs
public ActionResult GetCaptcha(string prefix, bool noisy = true)
{
    var rand = new Random((int)DateTime.Now.Ticks);
    int a = rand.Next(1, 5);
    int b = rand.Next(1, 5);
    ...
    Session["Captcha" + prefix] = a + b;
```

The challenge is a sum of two numbers in 1–4 (answer 2–8, ~7 possibilities), and `System.Random` is non-cryptographic. This provides almost no bot resistance and does not meaningfully mitigate M2.

**Remediation:** Replace with a real CAPTCHA (e.g., reCAPTCHA/hCaptcha) or a much larger, cryptographically generated challenge, and rely on server-side lockout/rate limiting.

### M7 — Stack traces returned to the UI
**CWE-209** · multiple admin controllers (e.g., `ProductsController.SaveOrEdit`, `DeleteConfirmed`)

```156:156:EImece/EImece/Areas/Admin/Controllers/ProductsController.cs
ModelState.AddModelError("", AdminResource.GeneralSaveErrorMessage + "  " + ex.StackTrace);
```

Raw `ex.StackTrace` is surfaced in the view. Scoped to authenticated admins, but still leaks internal paths/implementation details and is a poor pattern if any of these surfaces reaches non-admins.

**Remediation:** Log the exception server-side; show a generic message to the user.

### M8 — Mass assignment / over-posting on public model binding
**CWE-915** · `ProductsController.Review(ProductComment)`, `PaymentController.CheckoutBillingDetails/ShoppingWithoutAccount(Customer)`

Whole entities are bound from request bodies (`ProductComment`, `Customer`) including fields the client shouldn't control (`ProductId`, `Position`, `Lang`, address/customer-type fields, etc.). `ProductComment.IsActive` is fortunately forced to `false`, but other properties are attacker-settable (e.g., attaching a review to an arbitrary `ProductId`, or setting customer fields used downstream).

**Remediation:** Bind to explicit view models / use `[Bind(Include=...)]` allow-lists; map only expected fields to entities server-side.

## LOW / Hardening

- **L1 — No Content-Security-Policy; deprecated `X-XSS-Protection`.** `Infrastructure/SecurityHeadersHttpModule.cs` sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, but no CSP. Given the multiple `Html.Raw` sinks, add a restrictive `Content-Security-Policy`. `X-XSS-Protection: 1; mode=block` is deprecated (harmless, can be dropped). Note `PreSendRequestHeaders` is used — fine for classic pipeline.
- **L2 — Upload/DoS limits.** `maxRequestLength="512000"` (~500 MB) and `executionTimeout="36000"` allow large-payload resource exhaustion. Lower to realistic limits.
- **L3 — Dynamic DDL from spreadsheet/CSV column names (SQL injection surface).** `ExcelHelper.ExecuteSqlCommand` runs `GetCreateTableSql(dt)` built from imported column/table names via string concatenation (`EImece.Domain/Helpers/ExcelHelper.cs`, ~line 765/791). Admin/console-only, but validate/quote identifiers.
- **L4 — Non-cryptographic randomness for generated filenames.** `FilesHelper.GetFileNames` uses `new Random()`; predictable but low impact since images are re-encoded and extension-checked (`IsImage`) — the upload path is reasonably safe against web-shell upload.
- **L5 — Legacy `RijndaelManaged` with 256-bit block + PBKDF2 iteration count 1000.** `StringCipher.cs` uses a 256-bit block (non-AES Rijndael) and only 1000 KDF iterations. Prefer `Aes` (128-bit block) and raise iterations (≥100k) or use Data Protection API. (The design otherwise correctly randomizes salt/IV, unlike C2.)
- **L6 — Deserialization of DB-stored JSON into typed models** (`JsonConvert.DeserializeObject<...>(item.ShoppingCartJson)` in `PaymentController`). Not `TypeNameHandling.All`, so not classic insecure deserialization, but ensure default `TypeNameHandling.None` remains and the JSON source stays trusted.

---

## What looked correct (to avoid churn)

- **Open redirect is handled** — `RedirectToLocal` and `SecurityHelper.TryGetSafeReferrerRedirect` use `Url.IsLocalUrl` before redirecting.
- **Order access control** — `PaymentController.CanViewOrder` verifies ownership before showing an order.
- **Admin area authorization** — `BaseAdminController` is decorated with `[AuthorizeRoles(Administrator, Editor)]`; admin deletes use `[HttpPost] + [ValidateAntiForgeryToken]`.
- **TLS pinned** — `ServicePointManager.SecurityProtocol = Tls12` (no TLS 1.0/1.1).
- **EF/LINQ data access** is parameterized; the raw-SQL `DatabaseUtility`/`DbMigration` paths use `SqlParameter` arrays.
- **Auth POST actions** (`Login`, `Register`, `ResetPassword`, `ForgotPassword`, `ExternalLogin`, `LogOff`, `Manage*`) consistently carry `[ValidateAntiForgeryToken]`.

---

### Suggested remediation order
1. Rotate DB password and the query-string key; remove hard-coded secrets (C1, C2).
2. Stop logging tokens/PII (H2) and fix production config `debug`/`httpRuntime` (H3).
3. Encode the search output and audit `Html.Raw` (H1, M4).
4. Enable lockout, generic auth errors, secure cookies, real captcha (M1, M2, M3, M6).
5. Convert GET mutations to POST + anti-forgery; tighten model binding (M5, M8).

Want me to implement any of these? I'd suggest starting with the low-risk, high-value fixes (H1 output encoding, H2 log scrubbing, M1/M3 auth hardening, and moving the secrets out of config), which I can do without changing existing functionality.
